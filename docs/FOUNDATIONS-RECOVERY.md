# BESA foundations and recovery

BESA uses GitHub for source and release checks, Netlify for the company site and office, and Supabase for authentication, private records and documents. The foundations release keeps these platforms and preserves existing records.

## Access and hosting

Office administrators are linked to their Supabase user UUID. Database policies require administrator membership and a verified authenticator session once enrolled; the global MFA requirement is enabled after the new sign-in screen is published. Candidate invitations remain separate expiring capabilities and do not create office accounts. Public account registration is disabled.

Netlify builds the locked dependencies with `npm ci` and `npm run build`. The published folder contains only allowlisted website assets. Office and candidate pages are served directly with CSP, no-store, frame restrictions, HSTS and no-referrer headers. Browser scripts load from the company domain. GitHub Pages publishes only redirects for old bookmarks, preserving invitation fragments to the fixed company domain.

Shared driver checklists use versioned saves. A stale editor gets a conflict and keeps their browser draft. Reload saved progress replaces the draft only after confirmation; a failed load retains it. Driver evidence is private, limited to 8 MB PDF/JPEG/PNG/WebP, checked for file signatures and linked to a driver UUID. Saved evidence is not publicly addressable. Existing candidate document access remains private and expires after 60 seconds.

## Daily encrypted backups

The `Encrypted BESA backup and restore rehearsal` GitHub workflow runs at 01:43 UTC daily and can be run manually. GitHub schedules can be delayed. A failed run must be investigated; a missing or failed run is not a successful backup. Keep GitHub Actions failure notifications enabled for the repository owner.

Each successful run exports a consistent database snapshot of all public business tables, authentication users and identities, MFA factors, security settings and schema definitions. The encrypted `snapshot.pgp` includes table columns/defaults, sequences, functions and their permissions, constraints, indexes, triggers, row policies and grants. Each Storage document is streamed separately from Supabase into its own encrypted `documents/<random UUID>.pgp` part. Names, paths, ownership and plaintext hashes remain inside the encrypted snapshot. The public `verified.json` contains only counts and verification results.

The runner decrypts only in memory, checks every document's SHA-256 and byte count, then reconstructs database rows in an isolated schema and compares their content. That row rehearsal removes its own isolated schema in the same transaction. A changed source object, failed download, missing part or failed integrity check prevents publication of a complete archive. Existing successful backups are never overwritten. Unchanged objects from the previous successful artifact are decrypted and verified again before their encrypted parts are copied into the new independent archive. This avoids repeatedly downloading the same document bytes from Supabase. If a cached part is damaged or unavailable, it is downloaded afresh.

Only the completed archive directory is uploaded to GitHub; interrupted `.pending-*` directories are excluded. Each successful artifact is self-contained and retained for up to 90 days, subject to the account's storage quota. The old v1 reader remains available for retained single-file archives.

The job token permits export and isolated rehearsal; it cannot restore or overwrite production. Its hash and recovery public key are stored in the private database schema. The private key and passphrase are GitHub encrypted Actions secrets, never public repository files. A second local copy uses a passphrase-encrypted private key and Windows user-bound DPAPI protection outside the repository. Losing the Windows account requires recovery through an owner-controlled GitHub workflow using the existing secrets; GitHub does not display secret values again.

The free plan has no Supabase managed database backups or point-in-time recovery. BESA chose to remain on free. The former 64 MB aggregate document limit has been removed: document bytes no longer occupy the metadata JSON request or accumulate in Edge Function memory. The individual app upload limit remains 8 MB. Database metadata still has a 96-million-character request limit; unexpected partitioned tables/views/foreign tables fail closed until explicitly supported. This is recovery tooling for the captured BESA schema, not a replacement for PostgreSQL's general-purpose dump tooling.

Free capacity is finite: Supabase Free includes 1 GB file storage and 5 GB egress, while GitHub Free includes 500 MB artifact storage shared with Packages. GitHub's account Actions budget was checked on 21 October 2026 and already blocks additional paid usage at $0; included-usage alerts are on. No paid plan, add-on or billing limit was increased. Keeping 90 complete daily archives of a large document library may exceed free capacity even though a single backup succeeds. Investigate failure notifications and usage alerts before that point, and preserve the last good artifact plus an owner-controlled encrypted offline copy. Do not silently discard documents, label a partial backup complete, delete old archives to make room, or promise unlimited retention. Standard public-repository runners are free; artifact capacity still needs monitoring. See [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions) and [Supabase pricing](https://supabase.com/pricing).

## Recovery procedure

1. Stop writes during a real recovery incident. Record the last successful workflow, archive timestamp, verification manifest and deployed Git commit. Preserve the original archive.
2. Download a successful encrypted artifact from GitHub Actions. Verify its SHA-256 against its manifest. Use the recovery key and passphrase through an owner-controlled process; never paste them into chat, public logs or repository files.
3. Decrypt in a private recovery environment. `scripts/run-backup-job.mjs` performs a fresh v2 export and row rehearsal without restoring production. For a downloaded v2 artifact, `readArchive` and `verifyPart` in `scripts/backup-v2.mjs` validate its encrypted snapshot and each encrypted document. V1 checkpoints can still be validated with `scripts/recovery-key.mjs verify PATH` on the protected Windows account.
4. Create an EMPTY separate Supabase project in the existing organisation only after confirming it is free. Never change or reset the production database password. `scripts/recovery-snapshot.mjs schema-sql ARCHIVE TARGET_REF` and `data-sql ARCHIVE TARGET_REF` generate the two restore transactions from the encrypted schema and rows. Pipe the generated SQL privately to that separate database; data SQL contains password hashes, factor secrets and private records, so never display it in chat, public CI logs or saved plaintext files. Both tools reject the live project reference; the schema transaction also rejects a nonempty public schema or existing auth users, and the data transaction rejects existing recovery rows. Restore schema first, then rows and constraints/policies/grants. Auth generated columns are excluded from inserts. No DROP, TRUNCATE or overwrite operation is emitted.
5. Upload documents into the recovered private buckets using `scripts/restore-document-archive.mjs ARCHIVE`, with `BESA_RECOVERY_PROJECT`, that NEW project's `BESA_RECOVERY_SERVICE_KEY`, and the established recovery-key environment variables supplied privately. The tool rejects the production project, verifies the archive first, uses `upsert:false`, and downloads every recovered object to compare bytes and hashes. A resumed restore accepts an existing object only when identical; a differing object is preserved and stops recovery. Never reuse the production service key or put keys in command arguments. Restore Auth URL/redirect settings, disabled public signup, password policy and MFA provider settings separately; those project-level settings and Edge Function secrets are not database rows. Deploy the backed-up application and Edge Function sources with new-project credentials, and verify before changing the production domain. Existing sessions must sign in again because project keys differ.
6. Compare fresh recovered snapshots with `scripts/compare-recovery.mjs ORIGINAL RECOVERED`. Test administrator MFA, non-admin denial, anonymous denial, candidate invitation boundaries, operational workspaces, saved-row conflicts and every private document before cutover. Daily isolated row rehearsals do not replace periodic fresh-project exercises. No measured full-disaster recovery time or automatic DNS failover is claimed.
7. Have the BESA owner review the verified recovery before switching production. Never restore over live records as a test. Restored finance drafts remain drafts and do not issue payments or invoices.

## Completed recovery exercise — 21 October 2026

A separate free project, `BESA Recovery Test 2026-10-21`, was created in the existing BESA organisation. Before inserting test data, the restored snapshot matched all 69 source rows and the captured tables, sequences, enums, functions/permissions, constraints, indexes, policies, triggers and grants exactly. This included 57 vehicles, 2 drivers and the administrator's authentication identity and MFA factor. No production rows were restored or overwritten.

Real new-project authentication proved that the cloned administrator could sign in and complete the restored authenticator; an AAL1 session was blocked and an AAL2 session could access the recovered operational records. A separate synthetic non-admin's password sign-in worked but database reads/writes and private files were denied. Anonymous access was denied. Checklist save/conflict handling, workspace history sequence writes, and private evidence upload/signed viewing passed. No login email was sent and production authentication was not contacted by the test harness.

The exercise then backed up 11 synthetic private files totalling **73,400,328 bytes** (ten incompressible 7 MiB files plus one tiny test file), exceeding the former 64 MB cap. A second independent backup reverified and reused all 11 encrypted parts with **zero document bytes downloaded from Supabase**. After removing only those synthetic files in the recovery project to simulate loss, all 11 were re-uploaded from the encrypted archive and downloaded again; sizes and SHA-256 hashes matched. Production had no Storage files at the checkpoint, so these test files were created only in recovery. The guarded `besa-recovery-validation` function and its auth-detail RPC are test-only and must never be deployed to production. Preserve the recovery project and encrypted archives after the exercise; pause the test project when finished.

## Release and rollback

Changes must pass the `foundations` check before merging to main. Netlify then builds from main. Verify the deployed commit and security headers on `/`, `/office/`, `/office/rota.html` and `/onboarding/`. Roll back website code using Netlify's previous successful deploy if necessary. Keep the additive database schema and backups; do not drop tables to roll back a visual release. Emergency authenticator recovery is an owner identity-verification procedure in Supabase, not a bypass in the public app.

Runtime dependency auditing reports no production dependency vulnerabilities at this release. Four low-severity development advisories remain in Browserify's unused elliptic/signing dependency chain. Excel's browser bundle includes only its required hashing and random-salt implementations, excluding that signing code. Leaked-password checking is unavailable on the chosen free plan. Password policy, MFA and restricted registration still apply.
